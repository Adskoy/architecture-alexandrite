# Задание 2. Мониторинг

## 1. Анализ as-is диаграммы C4 в контексте планирования мониторинга

Взглянем на имеющуюся систему:

![as-is](../Task1/as-is.jpg)

Если здесь изображена истина, то в системе отсутствуют средства для мониторинга, логирования и трэйсинга.
Имеется лишь не отображённая на схеме Яндекс.Метрика,
которая предоставляет лишь информацию о пользовательских действия в магазине.

RUM, безусловно, является важным источником данных для повышения удовлетворенности пользователей,
но в текущей ситуации он практически бесполезен. К тому же, помимо непосредственно магазина, у нас есть
еще 2 веб-портала для других групп пользователей, мониторинг которых не производится вовсе.

## 2. Мотивация

Прямо сейчас ситуация такова: 3 из 4 заявленных групп пользователей недовольны опытом взаимодействия с системой. 
Это:

- Пользователи магазином - на срыв сроков изготовления заказа;
- Бизнес-пользователи - также на срыв сроков изготовления заказа;
- Операторы MES - на долгую загрузку списка заказов.

Чтобы бизнес не схлопнулся, эти проблемы надо решать. А чтобы их решать, необходимо знать, в чём их первопричина.
На данный момент мы можем оценить систему лишь поверхностно, что позволить максимум выдвинуть предположения по
оптимизации (например, срыв сроков может быть обусловлен самостоятельным назначением операторов на заказ -
что им сложно сделать из-за тормозящей страницы с заказами). Но для того, чтобы разобраться с первопричиной 
проблемы, нам нужны специализированные средства.

Можно провести небольшую аналогию. Представим, что система - это живой организм. Тогда выявленные нами проблемы -
это симптомы какого-то недуга. В таком случае мониторинг, трейсинг и логирование заменят нам 
рентген, УЗИ и МРТ - процедуры, в целом, схожие (просмотр внутреннего состояния системы), но с 
разными подходами и служащие для разных целей. Конкретно в этом случае мониторинг есть рентген - общий снимок
состояния части организма.

Внедрение мониторинга, естественно, потребует затрат. Однако, затраты эти будут небольшими в контексте всего
проекта. Инструментом для наблюдаемости системы был выбран OpenObserve - полноценная замена ELK-стэка и имеющейся
Яндекс.Метрики. Он прост в настройке и менее требователен к хранилищу, его интеграция уложится в один спринт - и тот неполный.
К тому же, затраченные на внедрение мониторинга средства позволят идентифицировать и устранить имеющиеся
проблемы, стоимость которых несоизмеримо выше.

Есть еще один явный плюс внедрения мониторинга - репортинг. Помимо технических метрик можно настроить сбор
бизнес-показателей, которые можно чуть ли не реальном времени показывать на дашбордах, а не дергать пользователей
CRM, заставляя их тратить время на построение графиков в экселе.


## 3. Выбор подхода к мониторингу

Их будет не один, а два - бэкэнды пойдут по `Four Golden Signals`, а для фронтэндов используем 
не упомянутый в уроке `Real User Monitoring` за неимением других стратегий отслеживания фронтэндов.

Четыре золотых сигнала наиболее универсальный подход к мониторингу, который покрывает как простые REST-апи,
так и системы пакетной обработки (за таковую примем MES API, что по несколько минут обсчитывает полигоны).

Какие технические метрики нам необходимы? Вообще все - чем больше, тем лучше. Но если необходимо 
конкретизировать до списка, то вот минимальный набор:

- Число dead letters в RabbitMQ (показывает, сколько заказов из CRM отвалились, не дойдя до MES);
- RPS для API магазина и MES (определяем нагрузку на публичный апи для частников и B2B);
- RPS per user для MES с ярлыком `user_id` (смотрим, сколько нагрузки генерируют бизнес-пользователи);
- CPU & RAM utilization для всех 3 бэкэндов (позволит оценить загрузку контейнеров и настроить более точный скейлинг инстансов);
- RAM utilization для бд магазина (это витрина, поэтому надо покрыть все места, где может возникнуть затык);
- Latency для бд магазина (юзер икспириенс, все дела);
- Число соединений для БД магазина (опять же, магазин лагать права не имеет);
- Число соединений для БД MES (мб тормоза операторов связаны с лимитом пула соединений);
- Размер S3 хранилища (модели занимают много места, много места стоит денег - что-то можно и удалить);
- Размеры бд магазина и MES (скейлинг тратит деньги на облако + большой размер это повод сделать шардинг);
- Число `500` статусов для всех апи (определяем самое больное место);
- Число `200` статусов для апи магазина (смотрим, сколько всего запросов обрабатывает самый нагруженный компонент);
- Kb transferred для апи магазина и MES (определяем объем входящего трафика от пользователей)

Дополнительно не из списка я бы накинул еще:

- 99 перцентиль времени выполнения запроса, ярлык `url` (выявляем слабые места в апи)
- Число `400` статусов для всех API (400 статусы означают, что пользователь или фронтэндер косячат, а бэкэнд - нет);
- Kb transferred для S3 хранилища (оно у нас как CDN, будем мерять по нему, помогло ли кэширование на клиенте);
- RAM utilization для инстанса RabbitMQ (если шина перегружена, то и сообщения могут отваливаться).

Также мы можем собирать бизнес-метрики:
- DAU/MAU (сколько юзеров за день/месяц);
- Конверсия пользователя в заказ (сколько из активных пользователей что-то реально заказывают);
- Загруженность операторов с ярлыком `operator_id` (сколько заказов выполняет в среднем оператор MES);
- Сложность заказа (если заказы простые - нанимаем операторов, если они сложные - повышаем квалификацию имеющимся).
- etc etc etc

## 4. План действий

Грубыми мазкам процесс внедрения мониторинга получается примерно следующим:

1. Разворачиваем тестовый инстанс `OpenOpebserve`
2. Подключаем `Opentelemetry` в бэкэндах `Shop` и `MES`;
3. Деплоимся в dev-окружение и проверяем работоспособность;
4. Делаем продакшн-инстанс `OpenObserve` (on-premise или просто покупаем в облако);
5. Настраиваем в нем авторизацию, RBAC, стриппинг чувствительных данных (по типу адресов доставки);
6. Деплоимся в release-окружение, проверяем работоспособность;
7. Пускаем всё добро в продакшн;
8. Подключаем `RUM` от openobserve в CRM и MES фронтэндах, убеждаемся что оно работает;
9. Грохаем Яндекс.Метрику в фронте магазина и зменям ее на openobserve.
10. ???
11. PROFIT

В итоге мы получаем ту же самую систему, но с полной прозрачностью через OpenTelemetry, которая отчитывается 
в легко настраиваем и дешевый сервис мониторинга. 

>⚠️ Яндекс.Метрика, де-факто, стандарт для таких целей, поэтому вовсе не обязательно заменять её на что-то другое -
> можно просто добавить ее в 2 непокрытых фронта. Так и так на выходе мы получим дашборды с метриками, а 2 их источника
> можно и графаной/повербиаем/etc объединить;

## 5. Определение показателей насыщенности

В системе у нас 3 группы компонентов под нагрузкой: API, базы данных и RabbitMQ;

Для API и RabbitMQ насыщенность измеряется следующими показателями:

- Процент использования CPU и RAM. Раз уж у нас EC2 инстансы, то при достижении пороговых значений они должны 
скейлиться автоматически - например, [Azure](https://learn.microsoft.com/ru-ru/azure/architecture/best-practices/auto-scaling) 
добавляет инстанс при средней утилизации >70% и убавляет при падении ниже 50%.
Нужно также настроить скейлинг по расписанию (например, перед праздниками). Вся необходимая реакция по этой 
метрике - уведомление администратора о новых/убитых инстансах.
- MES API имеет дополнительный показатель - длину очереди. При ее превышении заказы начнут отваливаться,
о чем необходимо уведомить всех причастных (смской/месенджером/etc) и создать инцидент в гитлабе (ну или что там есть);

Базы меряются по следующим показателям:

- Дисковый I/O. Если мы не успеваем читать/писать, это опять-таки должно быть донесено до админа, а причастная апишка
должна начать троттлить запросы.
