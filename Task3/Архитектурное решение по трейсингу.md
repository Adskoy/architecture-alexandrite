# Задание 3. Трейсинг

## 1. Анализ системы в контексте планирования трейсинга

Заказ имеет следующий жизненный цикл:

- `INITIATED` [онлайн-магазин] — пользователь завёл новый заказ или положил товары в пустую корзину.
- `FILE_UPLOADED` [онлайн-магазин] — пользователь загрузил файл с 3D-моделью или создал его с помощью конструктора.
- `SUBMITTED` [онлайн-магазин] — пользователь нажал на кнопку «Сделать заказ».
- `PRICE_CALCULATED` [MES] — система посчитала стоимость заказа.
- `MANUFACTURING_APPROVED` [CRM] — заказ подтверждён, его можно отдавать в производство.
- `MANUFACTURING_STARTED` [MES] — оператор взял заказ в работу.
- `MANUFACTURING_COMPLETED` [MES] — оператор выполнил заказ.
- `PACKAGING` [MES] — оператор начал упаковывать заказ.
- `SHIPPED` [MES] — заказ отправлен покупателю.
- `CLOSED` [CRM] — заказ завершён. Он закрывается после получения сообщения от транспортной компании или вручную.

При этом CRM и магазин делят между собой базу данных, так что физически заказ перемещается только между
CRM и MES, где благополучно и отваливается. Соответственно, трейсингом покрыть необходимо _минимум_
апишки CRM и MES.

Для трейсинга нам хватит стандартного набора данных с парой наворотов:

- user id;
- instance ip;
- service name;
- timestamp_start;
- timestamp_end;
- tags;
- endpoint url;
- trace_id;
- span_id;
- parent_span_id;
- operation_name;
- order_id;
- user_id;

К счастью, кроме последних двух пунктов otel-агент подставит это всё за нас. 


## 2. Мотивация

В то время как метрики показывают что _что-то_ пошло не так, трейсинг показывает, где именно это случилось, так что
внедрение трейсинга позволит идентифицировать проблемные участки в системе. Он показывает где конкретно находится 
затык в приложении, что существенно сокращает время на анализ инцидентов и, следовательно, время до релиза фикса.

Дополнительно, используя трассировку разработчик будет ясно видеть граф взаимодействия сервисов друг с другом,
что позволит обнаруживать проблемы с прохождением запроса еще на этапе отладки. Возвращаясь к аналогии с 
живым организмом, трассировка запросов это, по сути, УЗИ - показывает внутреннее течение процесса в динамике.

Влияние трейсинга на технические метрики:

- Сокращение времени выполнения запроса (смотрим на каком этапо оно велико, оптимизируем - вуаля);
- Снижение числа 500-х статусов (сразу видим в каком месте отвал и моментально фиксим);
- Снижение потребления CPU/RAM (оптимизировали пайплайн прохождения запроса - освободили немного ресурсов);

Влияние трейсинга на бизнес-показатели:

- Снижение операционной стоимости (разрабочик вместо археологических раскопок в поисках проблем просто чинит сломанное и работает себе дальше);
- Удержание пользователей (быстрый беспроблемный заказ ведет к повторному и привлечению клиентов через "сарафанное радио");
- Оптимизация производственных ресурсов (заказы перестают отваливаться -> незанятым операторам есть чем заняться);

TLDR. Мы добавляем в набор сервисов экземпляр `OpenObserve`. Далее мы настраиваем все что можно на отправку данных в него через otel-агенты - S3 будет слать объем 
занятого места, базы  - потребление ресурсов и I/O, апишки - CPU, RAM, RPS, etc. В довершение ко всему MES & CRM API будут также писать трейсы с данными, указанными выше.

Если забуриться в трассировку, то выглядеть это будет вот так:

У нас появляются джва маршрута для отслеживания заказов: CRM --> MES для только что подтвержденных и MES --> CRM для успешно отправленных заказчикам.

MES API при этом пораждает несколько span'ов, тк мы отдельно тейсим операцию обработки заказа и операцию обсчёта его стоимости.

## 4. Компромиссы

Да, в общем-то, их особо и нет. Можно счесть за компромисс то, что на текущем этапе трассировка не внедряется в API магазина, так как он не содержит вызовов 
других сервисов, а стало бы трейсинг там был бы излишним - хватит и логов.

Также следует упомянуть, что внедрение трейсинга в MES API может оказаться более трудозатратным, чем в CRM API, ибо это сторонняя система. 
Благо она куплена со всеми потрохами как раз на такой случай, а в команде есть 2 шарписта, так что доработка API с целью насыщения 
трейсов нужными данными технически может быть проведена.

## 5. Безопасность

Так как трейсы (да и метрики) содержат чувствительную информацию, следует предпринять несколько шагов для обеспечения информационной безопасности.

1. **(На случай On-Premise установки)** Сервис сбора статистики полностью убирается за DMZ - доступ к нему имеют только люди в периметре организации;
2. Внедрить механизм аутентификации по корпоративной учётке;
3. Разделить доступный пользователям функционал по RBAC - например, девопсер будет видеть только дашборды с метриками, разработчик - трейсы, продакт - метрики веб-порталов;
4. Стрипать чувствительные данные - если в строке запроса передается, например, токен доступа, его нужно подменить строкой-заглушкой.

Все эти пункты доступны в форсящемся мной openobserve из коробки, большинство даже мышкой настраиваются.
